# Нагрузочное тестирование (Этап 6, раздел 6 ТЗ)

## Важная оговорка

Скрипты в этой папке **написаны, но не запускались** против живого стека —
в среде, где я это писал, нет сети и не подняты Postgres/Redis/backend
одновременно. Ниже — рабочий инструмент для прогона + анализ вероятных узких
мест по чтению кода (что можно сказать заранее), но реальные цифры (P95,
пропускная способность, где именно начнёт деградировать) даст только
фактический прогон на вашем железе/окружении. Не выдавайте цифры "из головы"
за результат теста — их просто нет, пока вы не запустите `k6 run` сами.

## Как запустить

Нужен установленный [k6](https://k6.io/docs/get-started/installation/) и
поднятый backend (Postgres + Redis + `npm run dev` или собранный `npm run
build && npm start`) с известным `TELEGRAM_BOT_TOKEN`.

```bash
# 1. Сгенерировать N подписанных initData тем же токеном, что в backend/.env
cd backend/loadtest
node gen-init-data.mjs "$TELEGRAM_BOT_TOKEN" 500 > users.json

# 2. Прогнать сценарий (см. ramping-стадии и пороги внутри k6-script.js)
k6 run -e BASE_URL=http://localhost:3000/api -e USERS_FILE=./users.json k6-script.js
```

Тестовые пользователи создаются в БД с `telegramId` от `900000000` и выше —
после теста их можно удалить одним запросом:

```sql
DELETE FROM "User" WHERE "telegramId" >= 900000000;
```
(экономические каскады — `Transaction`, `GameSession`, `AdView` и т.д. —
имеют `onDelete` по умолчанию Prisma, то есть RESTRICT; либо удалите дочерние
записи первыми, либо временно настройте `onDelete: Cascade` для теста —
удобнее всего просто использовать отдельную тестовую БД, не прод/staging).

## Что смотреть в результатах k6

- `http_req_duration` (p95/p99) по каждому эндпоинту — GET `/me` и POST
  `/games/dice/play` должны быть на порядок быстрее, чем POST
  `/games/slots/play` (больше RNG-логики) или POST `/games/crash/start`
  (создаёт WS-сессию).
- `http_req_failed` — рост к концу самой высокой ramping-стадии (500 VU)
  обычно означает, что вы упёрлись в пул соединений Postgres (см. ниже), а не
  в CPU Node-процесса.
- Смотрите отдельно на `daily-bonus/claim` — в сценарии он вызывается
  КАЖДЫЙ визит, поэтому в реальности почти всегда будет отвечать быстрым
  "уже получено" (см. economyService.ts), а не считаться полноценным раундом.

## Вероятные узкие места — по коду, не по прогону

- **Один процесс Node, без кластеризации.** `server.ts` поднимает один
  Fastify-инстанс. На многоядерной машине это использует одно ядро — если
  прогон покажет, что CPU процесса под 500 VU в потолке, а остальные ядра
  простаивают, первый шаг — `node:cluster`/PM2 в режиме cluster или несколько
  контейнеров за балансировщиком (см. следующий пункт про WebSocket).
- **Пул соединений Prisma не настроен явно** (`db/prisma.ts` — просто `new
  PrismaClient()`). Дефолт — `num_physical_cpus * 2 + 1`. Под нагрузкой это
  может оказаться и мало (много одновременных запросов ждут свободное
  соединение — растёт p95) и много (упираетесь в `max_connections` самого
  Postgres, особенно если backend масштабируют на несколько инстансов). Если
  прогон покажет рост latency без роста CPU — это первый подозреваемый;
  настраивается через `?connection_limit=N` в `DATABASE_URL`.
- **Лидерборд и турниры считаются "на лету"** (`groupBy` по `Transaction`/
  `GameSession` за окно времени, см. `leaderboardService.ts` и
  `tournamentService.computeLiveScores`) — это самые тяжёлые SELECT'ы в
  системе, особенно на таблице `Transaction`, которая растёт с каждой
  ставкой. Если в реальном прогоне добавить их в сценарий с высокой частотой
  (в текущем сценарии — только 10% визитов), они, скорее всего, будут первым,
  что деградирует при росте объёма исторических данных — это ожидаемо и
  задокументировано как компромисс в `docs/ARCHITECTURE.md`.
- **Redis — общий rate-limiter для ВСЕХ игроков.** `lib/rateLimiter.ts` и
  `lib/antifraud.ts` делают `INCR`/`GET`/`SET` на каждый claim рекламы —
  дешёвые операции сами по себе, но при высокой конкурентности Redis
  становится единой точкой отказа для этой конкретной функциональности (не
  для игр — те не используют Redis вообще). Один инстанс `ioredis` без пула
  — для MVP-нагрузки достаточно, но стоит отдельно нагрузочно проверить
  именно `/ads/*/claim` под пиком (например, все игроки смотрят рекламу
  одновременно после пуш-уведомления).
- **WebSocket-стрим Краша (`/games/crash/stream`) хорошо ложится на
  горизонтальное масштабирование**, в отличие от многих наивных реализаций:
  состояние раунда полностью детерминировано и читается из `GameSession.result`
  в Postgres при подключении (не хранится в памяти конкретного процесса), так
  что любой инстанс backend может обслужить любой сокет — sticky sessions на
  балансировщике не нужны. Единственная цена — один `setInterval` (100мс) на
  каждое активное соединение; это чистый CPU без похода в БД на каждый тик,
  поэтому тысяч одновременных активных Краш-раундов один процесс, скорее
  всего, не выдержит раньше, чем упрётся Prisma-пул — но это тоже стоит
  подтвердить прогоном, а не считать доказанным.
- **AdsGram-клейм не идемпотентен на уровне HTTP-ретраев клиента** — только
  на уровне `adsgramImpressionId` (уникальный индекс в БД). Если тестовый
  скрипт или реальный клиент ретраит запрос с НОВЫМ impressionId после
  таймаута (вместо того чтобы просто повторить старый), это будет выглядеть
  как настоящий повторный показ, а не как баг идемпотентности — учитывайте
  при интерпретации метрик antifraud (`AdView.suspicious`) на нагрузочном
  прогоне: синтетические ID из `gen-init-data.mjs`/`k6-script.js` не
  привязаны к реальной скорости просмотра, так что soft-флаг сработает почти
  всегда при высокой VU-конкурентности — это ожидаемо для теста, не сигнал
  реальной проблемы.
